# A1 — The Action Loop: Prior Art on Action / Triage Models in Email & Digest Tools

> Research brief for spec item **A1**. ActionPulse is read-only today (it surfaces action items; you cannot act on them). This brief surveys how email and digest tools let users *act* on items, to inform whether/what ActionPulse should add. Status: research only. Confidence noted per claim.

## 1. TL;DR

- **The de-facto standard triage action set is small and stable:** **done/archive**, **snooze/defer**, **delete**, plus **reply** and **send-to-task**. Almost every modern client converges on these. ("Mark Done" + "Snooze" is the canonical pair, popularized by Mailbox in 2013 and now in Gmail, Outlook, Spark, Shortwave, Superhuman.)
- **Two UX patterns dominate:** **keyboard shortcuts** on desktop (single keys: `e`=archive/done, snooze on a one-key binding) and **swipe gestures** on mobile (left/right configurable to archive/delete/snooze/flag). Secondary patterns: **inline hover/quick-action buttons** and, more recently, **natural-language / AI** ("snooze 4 hours", smart replies).
- **`snooze` and `done` are *state transitions on a per-item lifecycle*, not deletes.** Done = remove from inbox but keep (archive). Snooze = hide until time T, then re-inject "as new" at top of inbox with a notification; both ship with **undo** and **cross-device sync**. This state model is the single most-copied idea in the category.
- **"Highest-value action" data is thin and should be treated cautiously.** The only hard public number is Google's: Smart Reply was ~12% of replies — but on the *Inbox by Gmail* product, not Gmail proper (low confidence as a general stat). General signal: most users *delete* by default rather than archive; "88% of emails need no action," so the dominant act is *dismissal*, not reply.
- **For a digest-first (daily batch) tool the calculus shifts:** there is no live inbox to keep at zero, so "archive" loses meaning; the high-value verbs become **done** (acknowledge an extracted item), **snooze→next digest** (defer to a later batch), and **send-to-task / quick-reply** (because the digest is the *only* touch-point that day). State must live in ActionPulse's own store and round-trip to the next digest, since the source (Exchange/Mattermost) is upstream and largely read-only.

## 3. Findings

**The standard action set converged ~a decade ago.** Mailbox (Gentry Underwood, 2013) introduced three things that defined the category — *swipe gestures, email snoozing, and auto-swipe* — and a task-centric framing of email. Its snooze was so popular "other email clients subsequently adopted similar functionality." ([phonearena](https://www.phonearena.com/news/Mailbox-for-iOS-and-Android-archives-your-emails-automagically_id55423), [thenextweb](https://thenextweb.com/news/mailbox-gets-updated-post-dropbox-acquisition-featuring-improved-snoozing-and-ui-fixes), [mailbird](https://www.getmailbird.com/what-happened-to-mailboxapp-com/)) Today every surveyed client offers some subset of **{done/archive, snooze, delete, reply, flag/to-do, send-to-task}**.

**`done` ≠ `delete` is a load-bearing distinction.** Shortwave's method is explicitly built around marking an email "Done," which "makes it disappear from your active inbox without being deleted" and is used "interchangeably with archiving but distinguished from deletion." ([Shortwave method](https://www.shortwave.com/docs/guides/method/), [clean.email](https://clean.email/blog/email-clients/shortwave-review)) The inbox-zero literature codifies the same split: archive if you might need it later, delete only if you never will. ([clean.email inbox-zero](https://clean.email/blog/productivity/what-is-zero-inbox), [jatheon](https://jatheon.com/blog/should-you-delete-or-archive-email/)) The decision frame behind all of this is GTD's **"4 Ds" / 5 Ds — Do, Defer, Delegate, Delete (+Archive)** ([Zawodny's original post](http://jeremy.zawodny.com/blog/archives/009311.html), [hostinger](https://www.hostinger.com/tutorials/inbox-zero-method)); Superhuman teaches a near-identical tree (handle-in-2-min / delegate / defer-with-deadline / archive / delete). ([Superhuman email-to-task](https://blog.superhuman.com/email-to-task-workflow/))

**`snooze` as a state model is remarkably uniform across tools:** (1) item is removed from the active view; (2) it is parked (Gmail "*Snoozed*" folder, Outlook "schedule", SaneBox "@SaneTomorrow" folder); (3) at time T it returns **"to the top of your inbox as if it were new,"** firing a fresh notification; (4) an **Undo / "Snoozed until…"** banner is offered immediately; (5) state **syncs across devices** ("snooze on phone → same state on desktop"). ([RightInbox](https://www.rightinbox.com/blog/gmail-snooze), [clean.email snooze](https://clean.email/gmail-snooze-feature), [Spark snooze](https://sparkmailapp.com/help/tips-tricks/snooze-emails)) SaneBox proves the same model works *server-side* with no client changes, by shuffling IMAP folders and resurfacing unanswered threads. ([SaneBox reminders](https://www.sanebox.com/help/139-reminders-overview-what-are-sanereminders-and-how-do-they-work))

**UX patterns split cleanly by surface.** Desktop/power users: **keyboard shortcuts** — Superhuman markets "nearly every action… without touching your mouse," `e` archive / `l` label / one-key snooze ([nickgray shortcut list](https://nickgray.net/superhuman/), [Superhuman PDF](https://download.superhuman.com/Superhuman%20Keyboard%20Shortcuts.pdf)); Shortwave uses `T`=to-do, `D`=delete ([Shortwave shortcuts](https://www.shortwave.com/docs/references/shortcuts/)). Mobile: **swipe**, with left/right user-mapped to delete/archive/read/flag/snooze (Outlook, Spark, Yahoo all expose this in settings). ([Outlook swipe](https://support.microsoft.com/en-us/office/customize-swipe-left-and-swipe-right-gestures-in-outlook-c8534c2e-1002-450d-a8f3-e53cc8e36b1d), [Spark swipes](https://support.readdle.com/spark/personalization/manage-emails-with-swipes)) A third pattern is **inline hover / quick-action buttons** (Gmail, Outlook OWA). The newest pattern is **natural-language / AI**: "snooze 4 hours" free-text (Shortwave) and suggested **Smart Reply** chips (Gmail).

**"Send to task" is overwhelmingly a forward-to-a-magic-address pattern.** Todoist, Things, and Asana *all* implement the same primitive: every account gets a unique inbound email address; forwarding a message creates a task that **links back to the source**, optionally parsing date/project/assignee. ([Todoist forward](https://www.todoist.com/help/articles/forward-emails-to-todoist-JPJ1V339), [Mail to Things](https://culturedcode.com/things/blog/2017/12/mail-to-things/), [Asana email](https://help.asana.com/s/article/email-tasks-to-asana?language=en_US)) Richer integrations add a 2-click button (Todoist Gmail add-on) and AI titling (Todoist "Email Assist"). ([Todoist Gmail](https://www.todoist.com/help/articles/use-gmail-with-todoist-YMVdMcAx)) Notably, **delegate** often falls out of the same mechanism — Things suggests giving your `@things.email` to a colleague so they can push to-dos to you. ([Mail to Things](https://culturedcode.com/things/blog/2017/12/mail-to-things/))

**Which actions are *most-used*? Honest answer: weak public data.** The cleanest hard number is Google's Smart Reply ≈ **12% of replies on mobile** — but the figure is for **Inbox by Gmail**, not Gmail itself, so treat as illustrative, not a general stat. ([Google Research](https://research.google/blog/efficient-smart-reply-now-for-gmail/)) Directional signals only: vendors report **"88% of emails need no action"** and that **most users delete (not archive) by default** — i.e. the single most-performed verb is *dismissal*. ([Superhuman inbox-zero](https://blog.superhuman.com/inbox-zero-method/), [leavemealone](https://leavemealone.com/blog/outlook-archive-vs-delete/)) No surveyed source published reliable comparative usage of snooze vs done vs send-to-task; vendor blogs are self-interested. **(Low confidence on any ranking beyond "dismiss > reply > defer.")**

## 4. Recommended minimal action set for a digest-first tool

ActionPulse delivers a **daily batch** (no always-on inbox), with the digest landing in a **terminal run** and/or a **delivered Mattermost message**. That changes the value of each verb. Recommended v1 set, smallest-that-works:

| Action | Why it's in the minimal set | State implied | Undo | Where it originates |
|---|---|---|---|---|
| **Done / Acknowledge** | The core verb of a digest: "I've seen/handled this item." Replaces "archive" (no inbox to clear). Suppresses re-surfacing of the same extracted item in future digests. | Per-item status `open → done` in **ActionPulse's own store** (source is read-only). Must dedupe future runs against done items. | Yes — toggle back to `open`; cheap if state is local. | **Both.** Terminal: one-key on the focused item. Delivered message: reaction/button (e.g. a Mattermost reaction maps to "done" — aligns with the existing reactions seam). |
| **Snooze → defer to a later digest** | The batch analog of email snooze: "not today, resurface this in tomorrow's / Monday's digest." | `open → snoozed(until=T)`; item is hidden from digests until T, then re-injected and flagged "(snoozed)" — mirror the universal snooze model (resurface-as-new + banner). | Yes — "un-snooze" returns to next digest immediately. | **Both**, but choices should be batch-granular ("tomorrow / next digest / +3 days / pick date"), not clock-precise. |
| **Send to task / Quick-reply** | Because the digest is the *only* touchpoint that day, the highest-leverage act is converting an item into action elsewhere. Mirror the proven forward-to-address pattern. | Usually **stateless** for ActionPulse (fire-and-forget), but should flip the item to `done` (it's been actioned). Capture a back-link to `evidence_id`/`source_ref` so the task references the original (satisfies P2 traceability). | Limited — once a task/reply is sent it's external; offer undo only on the local `→done` flip. | **Terminal first** (operator runs it); for Mattermost, a quick-reply could post back to the thread. Honors "read-only today" by making *outbound action* explicit and opt-in. |

Deliberately **excluded from v1** (defensible later, not now): **delete** (a privacy-first digest shouldn't tombstone source items; "done" already removes from view), **flag/star** (redundant with the digest's own urgency sections `my_actions`/`urgent`), **delegate** (subset of send-to-task), **label** (the digest is already sectioned).

**Cross-cutting implications:**
- **State store, not the source.** Exchange/Mattermost are upstream and read-only in spirit; action state (done/snoozed/until) must live in ActionPulse's store and be the authority that the *next* digest filters against. This is the SaneBox lesson (server-side state model) more than the Gmail one (client mutates the mailbox).
- **Idempotent re-surfacing.** Done/snooze only work if extracted items have **stable identity across runs** (so yesterday's "done" suppresses today's re-extraction of the same thing). This is the real engineering cost — likely the gating dependency, not the UI.
- **Undo is table-stakes** and easy when state is local: every surveyed tool ships an Undo/"snoozed until…" affordance.
- **Two origination surfaces** (terminal vs delivered message) means two action UIs: keyboard on the terminal, **reactions/buttons** on Mattermost. The existing reactions seam is the natural carrier for "done" from the delivered side.

## 5. Open questions / low-confidence

- **Usage ranking is under-sourced.** "Dismiss > reply > defer" is inferred from vendor stats, not measured; the 12% Smart-Reply figure is from a *retired* product. Do not size features on these. *(Low confidence.)*
- **Does a batch tool even need snooze, or just done?** If the next digest already re-ranks open items, "snooze" may be redundant with "leave it open." Worth a usage test before building. *(Medium.)*
- **Outbound action vs "read-only today" posture.** Send-to-task / quick-reply *write* somewhere (a task app, a Mattermost thread). That crosses ActionPulse's current read-only line and needs a product decision + likely consent gating (cf. existing MM consent UX). *(Decision, not research.)*
- **Item identity stability** across daily runs is assumed, not verified here — confirm against ActionPulse's extraction/dedupe before promising done/snooze. *(Verify in code.)*
- **Mattermost-side undo** for a reaction-driven "done" — reaction add/remove is a clean toggle, but multi-recipient/owner-channel semantics weren't researched. *(Low.)*
- **Snooze granularity** (clock-precise vs digest-granular) is a UX call; all email tools are clock-precise because they re-inject into a live inbox — that assumption doesn't hold for a batch. *(Medium.)*
